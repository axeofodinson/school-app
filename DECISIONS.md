## 2026-11-26 — Spaced revision (prompt 42)

160. **Spaced revision is two checks, at 7 and 30 days, and a check is a revision set on a due idea.** `concept_mastery.review_stage` means 0 not scheduled, 1 the 7-day check is next, 2 the 30-day check is next, 3 retained. 019 already schedules stage 1 at mastery or relief. db/037 adds an after-insert trigger on `practice_attempts` (kind `revision`, after 019's mastery trigger): for each concept that is due (next check ≤ the attempt's time + 12 h) and has at least `roundMin` (3) items in the set, ≥ 80 % passes (stage 1 → 2 at +30 days, stage 2 → retained) and less fails (back to stage 1 at +7 days, plus one open `revision` follow-up, merged into an open one). Fewer items, plain practice, or a set before it's due changes nothing. The band never drops from mastered. — Same bar as a follow-up round, so the learner meets one rule; the 12-hour window lets a morning lab session count for an evening due time; revision follow-ups already come last and never block (41). — Claude, prompt 42.
161. **Each check is one append-only `revision_checks` row; a nightly rollup turns them into `retention_daily`.** Rows are a few per learner per month (free tier); learners read their own, teachers those they teach, staff all; only the trigger writes. `retention_rollup(day)` (pg_cron 02:10 PKT for yesterday, re-runnable) writes per subject and stage: checks, passed, learners, and how many ideas are due now / over a week late. Teachers of the subject and staff read it; no names. This is LMS_AUDIT §5.12's 7- and 30-day retention measure (core `retentionRates`); dashboards (80) read the rollup, never raw attempts. — Live queries over attempts would cost egress and CPU every time a dashboard opens. — Claude, prompt 42.
162. **Prepare shows "Due for revision" below the follow-ups.** Due ideas (longest waiting first, with a 1-week / 1-month badge and "N days waiting") each have Revise (a set of up to 5 on that idea, sent as kind `revision`); the next three later ones show as one dashed line with "in N days"; a small line counts ideas remembered for a month. The after-set note previews the server's verdict with the same rule. Nothing due and nothing scheduled → the section is hidden. — The prompt asks for a due list in Prepare; keeping it below "Do these first" keeps fixing mistakes ahead of retention. — Claude, prompt 42.

## 2026-11-26 — Offline Learn packs (prompt 32)

156. **A pack is one chapter, built by an RLS-checked RPC, stored as immutable (id, version) entries.** `learn_pack(chapter, have)` (db/036) is SECURITY INVOKER, so it returns exactly what the online reader and practice would: active topics and concepts, each approved lesson at its live learn approval, practice items at the newest version the learner may read, never exam-only items or drafts. The device keeps one entry per lesson / item version and a per-user index; entries are shared between students on a shared device (versions are immutable and each user only reads entries their own request listed), and orphaned entries are removed when the last index that lists them goes. — No new table or access path; a shared Chromebook doesn't store the same chapter 30 times. — Claude, prompt 32.
157. **Delta refresh by version, not by timestamp.** The device sends `have` ("l:id" / "q:id" → version) for entries it still holds; unchanged entries come back as ids + versions only, changed or new ones with content, withdrawn ones are simply missing (so the next index drops them). A pack older than a day refreshes quietly when the lesson list or Downloads opens online. — Approvals change without touching `updated_at`, so versions are the only reliable signal; with nothing changed a refresh is ~45 % of the first download. — Claude, prompt 32.
158. **Big storage: IndexedDB on web, files on Android.** Packs don't go in AsyncStorage/localStorage (≈ 5 MB on web). Maths SVGs are fetched once per key and shared. Raster images and audio aren't in lesson blocks yet (figures are inline SVG), so packs carry none; video stays online-only and its scene fallback is in the blocks. — Fits a 4 GB Chromebook; nothing to add later but the asset list. — Claude, prompt 32.
159. **The web build is an offline app shell.** `public/sw.js` (registered in production web builds only) precaches every file `scripts/sw-manifest.mjs` lists after export (all route chunks, fonts, images, short sounds; ≈ 6.8 MB once per device), serves navigations network-first with the saved shell offline, and never touches Supabase requests. — A Chromebook that opened the app once in the lab can open a downloaded chapter at home with no Wi-Fi, including screens it never visited. — Claude, prompt 32.

## 2026-11-26 — Live exam view, item analysis, confirm to grades (prompt 51)

151. **Exam scores reach grades only when the teacher confirms.** `exam_confirm` (db/035) refuses while any paper is open (`exam_still_running`), writes each handed-in score through `record_grade` with reason "Exam result" (audited), stamps `results_confirmed_at/by`, and runs once (`already_confirmed`). Until then the scores live only on `exam_sessions`; `submissions` stays empty. — Teachers check papers (void, hand marking) before results become grades; CLAUDE.md: `record_grade` is the only grade write path. — Claude, prompt 51.
152. **Void a paper, never delete it, and only with a reason.** `exam_void_session(session, reason)` sets status `void` with `void_reason` / `voided_by`; void papers are not graded and drop out of item analysis. Refused after confirm. — History is never rewritten; a resit or a broken device needs a record of why. — Claude, prompt 51.
153. **Exam follow-ups on confirm, per concept, below the mastery weak line.** For each graded paper, a concept where right × 100 < weakPct × counted (blanks count as wrong; answers still waiting for a teacher's mark are left out) opens a `kind='exam'` follow-up, merged with an open one for the same learner + concept. — Same weak line as practice (MASTERY_DEFAULTS), so exams and practice agree on "weak"; exam follow-ups block all topics as designed in F-3. — Claude, prompt 51.
154. **One Realtime channel per open live view; it only triggers a throttled refetch.** db/035 adds `exam_sessions` to `supabase_realtime`; `log_exam_event` and saves touch `last_seen_at`, so one table carries joins, progress and flags. The teacher's screen subscribes to that assessment only (`assessment_id=eq.…`, RLS applies) and re-reads `exam_live` at most every 3 s, plus a 20 s poll while running; students never subscribe. A student quiet for 90 s shows as "gone quiet". — 40 students saving cost one socket and ~20 reads a minute: far inside the free tier's 200 connections. — Claude, prompt 51.
155. **Item analysis flags need 5 papers.** Easy ≥ 90 % right, hard < 30 %, trap = a wrong option picked by at least as many as the key and by 3+ (core `itemFlag`); the key is marked with a tick and the word "answer", never colour alone. Teachers only: the RPC returns keys. — Small classes and early hand-ins would otherwise flag noise. — Claude, prompt 51.

Tests and exams are never gated. A paused lesson stays visible with a lock and says why on tap, instead of hiding. — Keeps the rule in one tested place, works offline from the cached follow-ups, and a gate can't trap a child: relief (#137) and teachers (#142) both open it. — Claude, prompt 41.
142. **Teachers relax or restore a gate only through `gate_relax` / `gate_restore` (db/034), always with a reason, always logged.** Allowed for staff, or a teacher assigned this academic year to the learner's active class for that subject (or the whole class). Relax closes the follow-up as `relieved` / `teacher_relax`, carries the concept over and books a revision; restore reopens a relieved one with rounds reset, refusing if another is already open on that concept. Both write `gate_overrides`. — RLS stays the boundary (no direct writes); the log answers "who let them skip this?". — Claude, prompt 41.
143. **"Who's stuck" reads one RPC (`class_follow_ups`) grouped by idea, not raw tables.** Open follow-ups plus those closed in the last 14 days, subject-scoped for teachers, with name, admission number, band and the last teacher who acted. "Stuck" = open and at the relief limit minus one round. — One cheap call per class on the free tier; the teacher sees who needs them before relief kicks in. — Claude, prompt 41.
144. **Diagnose and follow-up rounds are practice modes, not new screens.** `diagnose` runs `pickDiagnostic` over the topic (size from `diagnosticSize`); `followup` runs a set of 6 on the one concept and carries `follow_up_id` on the row. Both start straight from a link (`?mode=…`), and the summary previews the round's outcome (pass / not yet / too few) before the server decides. — Reuses prompt 31's engine and sync queue; the server stays the judge (#137). — Claude, prompt 41.
145. **Home's subject mosaics now come from concept bands.** A subject with active concepts shows mastered / total and its weakest band; a subject without concepts falls back to tests done. A "Next up" card names the open follow-ups and links to Prepare. — Wireframe 7.1; the tests fallback keeps Home useful before content is imported. — Claude, prompt 41.

## 2026-11-26 — Mastery, follow-ups and diagnostics (prompt 40)

134. **The mastery rule, made exact.** Window = the latest answer of each of the last 5 distinct questions of a concept. Mastered = a full window, ≥ 80 % right, ≥ 1 hard (difficulty 3) answered **right**, and ≥ 1 answered right the first and only time it was seen. Weak = ≥ 3 in the window and < 60 % right. Mastered never goes back (the mosaic tile stays, #33; spaced revision re-checks it, prompt 42); carried over stays until weak or mastered. The result keeps `needs` (`more`, `accuracy`, `hard`, `fresh`) so the app can say what's missing instead of showing a percentage. All numbers live in `mastery_config`. — Claude, prompt 40.
135. **The server marks every practice row itself, and both upload paths feed mastery.** A BEFORE INSERT trigger re-marks each item from the raw answer with the exact version's key (`c` rewritten, unmarkable items get `x: 1`), and an AFTER INSERT trigger updates bands and follow-ups. So the app's existing sync-queue insert needs no change, `record_practice_attempt()` is the same insert with a report, and a retried upload (same id) changes nothing because no row means no trigger. Bands are always recomputed from all evidence, never incremented, so they can be rebuilt (retired question, account link, a repair). — Claude, prompt 40.
136. **Only diagnostics and revision open follow-ups; plain practice only clears them.** A follow-up gates Prepare (prompt 41), so it must come from a check the learner chose to take, not from free practice. Any attempt that leaves a concept mastered clears its open follow-ups. — Claude, prompt 40.
137. **A follow-up attempt is a round for every open follow-up on the concepts it touched.** ≥ 80 % right on ≥ 3 items of the concept clears it; otherwise rounds + 1, and at 3 rounds, or when no unseen approved practice item of the concept is left, it is relieved automatically (relieved, carried over, back for revision in 7 days, logged in `gate_overrides` with no actor). A relief opens nothing new, so nobody is trapped (LMS_AUDIT §3.5). Teacher notification of a relief is left to prompt 41. — Claude, prompt 40.
138. **Diagnostic order is deterministic and shared with the device.** Approved practice items of the topic's active concepts; per concept never-seen first (then longest ago), difficulties interleaved medium → easy → hard; concepts take turns, so the first k items cover k concepts; ties on question id. Size = the request, else `topics.diagnostic_size`, else 30, kept in 5–60, never fewer than the concepts or more than the pool. `diagnostic_items()` returns ids and versions only. — Claude, prompt 40.
139. **019 carries an identical copy of 018's marking function.** Production gets 018 only at the cut-over, but mastery must mark the same way as exams. Both files define `auto_mark_item`/`answer_text_norm` byte for byte; whichever runs last wins with the same body, and both smokes run the shared auto-mark vectors. Seed rows (`is_test_data`) are stored as given, because the seed writes its own mastery rows. — Claude, prompt 40.

## 2026-11-25 — Visual blocks: scenes, charts, widgets (prompt 33)

128. **A scene is split into a stack of standalone SVGs, one per layer, and each layer moves as a composited view.** `sliceScene()` (core) cuts the authored SVG at each layer, keeping paint order, re-opening the layer's ancestors (their transforms and styles) and copying `<defs>`/`<style>` into every slice. Each layer then tweens only transform + opacity on the UI thread, with no SVG re-render per frame, which is the cheapest path on a 4 GB Chromebook and the same on web and Android. Turning point = the layer's estimated box centre, or `pivots` in the block. — Claude, prompt 33.
129. **Widget geometry is redrawn on the UI thread from a compiled expression program, never `eval`.** The safe parser (prompt 21) builds a tree; `compileExpr()` flattens it to numbers and a 20-line stack machine runs it inside a worklet (`widgets/vm.ts`, a copy of core's `runProgram`, checked for parity in core tests). Sliders write snapped values into shared values; React only hears when a snapped value changes. — Claude, prompt 33.
130. **On a scene, ← → walk its steps before moving to the next part; Play never starts by itself.** Like builds on a slide. Off tier: Play shows one step per tap. Playback holds each caption long enough to read (1.6–4 s) and always has Pause (WCAG 2.2.2). — Claude, prompt 33.
131. **Predict questions veil the visual until answered (or skipped) and are never reused as a quick check.** The `predict_question_id` item shows under the stage as "Predict first"; answering lifts the veil (`predictReveal`). "Skip, just watch / try it" is always there, so nobody is stuck. — Claude, prompt 33.
132. **Chart `reveal: "series"` reveals on tap, not on a timer.** The first series shows; a "Show …" button grows the next from the baseline (`chartReveal`). Exams show the whole chart. Pie charts list values and percentages beside the pie; series differ by marker shape as well as colour. — Claude, prompt 33.
133. **Visual text on the stage is always diagram ink, and graph axes stay left-to-right in Urdu.** The stage is paper-white in both themes (§7b.2), so theme text colours would vanish in dark mode. Readouts use symbols + units (`t = 2 s`, `v = 4 m/s`), the same in both languages; spoken labels are translated. — Claude, prompt 33.

## 2026-11-25 — Practice engine (prompt 31)

117. **One engine, four modes, no new migration.** `packages/core/src/practice` selects (practice, topic drill, smart review, retry-wrong), scores (autoMark, so practice and exams can never disagree) and builds the row; modes are configs. Practice reads `question_versions` through the 017 + 032 student policy (only the version with a live practice approval, so its key is meant for instant feedback); exam items never come this way. Smart review maps to `kind = 'revision'`, the rest to `'practice'`. Types the device can't mark (long answer, file, tap_image for now) are left out of sets. — Claude, prompt 31.
118. **Selection order: unseen anywhere first, then concept coverage, then the difficulty plan.** A set plans ~30 % easy / 40 % medium / 30 % hard, shown easy→hard; slots go round-robin over the topic's concepts; inside a concept, unseen items first, then the longest-ago seen. Smart review takes items last answered wrong, then items in a weak concept (< 60 % right with ≥ 2 answers), then items not seen for 7 days, oldest first, and falls back to a practice set (saying so) when there's nothing to review. Never repeats an item within a set (unit-tested for every mode across many seeds). — Claude, prompt 31.
119. **The row stays the documented shape, with two optional flags.** `items[]` is `{q, v, a, c, ms}`; `f: 1` when the learner flagged the question ("check this question") and `t: 1` when they opened the tip before answering, present only when set. Long text answers are cut to 200 characters, time is clamped to 0–30 min, one item per question, at most 50 items. `c` and `n_correct` are the client's own marking: prompt 40 must re-score from `a` with the key before using a row for mastery (a student can insert their own rows). — Claude, prompt 31.
120. **A set is saved when it ends, or part-way when the learner stops.** The set's client UUID is the row id, queued in the user's durable queue (shared with test submissions; the student layout sends both, the tests pill counts only tests) and remembered on the device so history counts it before it uploads. The topic's pool, maths and the learner's own recent sets (last 40) are cached in their storage namespace, so a topic opened once practises offline. — Claude, prompt 31.
121. **Feedback explains both sides; no streaks or time as success.** After Check: why the chosen option is wrong (`explanation.why_wrong`), the right answer, and why it's right; "See lesson" after a wrong answer. The summary shows only what was understood, by concept, weakest first, with "Drill this" and "Retry the N wrong". The timer is optional, off by default, digits only. Tips use `body.hint` when a question has one, else the concept name and a per-type strategy (the importer has no hint field yet). — Claude, prompt 31.

## 2026-11-25 — Teacher review queue (prompt 22)

107. **Approvals and reviews are written only through the review RPCs (db/032).** 017 let any teacher insert an approval for any question; now `review_question()`, `review_approve_many()` and `review_edit_question()` are the only writers, and a teacher may decide only on a question whose concept is in a subject they teach this year (`teaches_concept`, the same scope as the curriculum editors, #96); staff any. 109. **Decisions name the version on screen.** Every RPC takes the version the reviewer saw and refuses a different one (`review_stale_version`): two teachers clearing the same queue can't approve an edit neither has read. The screen reloads and says so.
110. **Approve needs "The answer is right" ticked; "Urdu reads naturally" is separate and logged.** Accuracy over speed for single items (V then A); `translation_ok` goes into `item_reviews` with the decision. Exam scope is never pre-ticked; the last scopes used carry to the next new draft. Bulk approve (wireframe "Approve 12") asks first and says the items weren't opened.
111. **Queue state is derived, not stored.** "Changes asked" = draft whose latest review on its current version is `request_changes`; reject = `retired` (kept). No new status values, no new tables. Queue reads run as the caller (`review_queue`, `review_counts`), up to 1,000 rows per filter; keyboard map lives in core (`reviewKeyAction`, physical keys so it works on an Urdu layout). Online only, like the importer (#100).

## 2026-11-25 — Content importer (prompt 21)

102. **The importer checks everything in the app, writes through one RPC, and never approves anything.** `packages/core/src/importer` turns a topic file into a report (schema via zod, exactly one correct option, concept + thinking level + difficulty on every question, English/Urdu presence, duplicates, visual-block checks); `db/031 import_content(chunk)` writes it, SECURITY INVOKER so the 017 policies still decide what a teacher may import, in chunks of 200 questions with client-made ids, so a retry or a double click writes nothing twice. Everything lands as `status = 'draft'`, version 1: approval is the review queue's job (prompt 22). A file with an error in its topic or concepts is refused as a whole; a bad question is simply left out with a reason, so one typo never blocks 200 good questions. — Claude, prompt 21, 2026-11-25.
103. **One rendered SVG per distinct maths expression, bank-wide (`math_svgs`), rendered in the browser at import time.** Thousands of MCQs per subject repeat the same `$x$` and `$\frac{a}{b}$`; storing the SVG inside each question body would cost tens of MB on a 500 MB free tier (TEST_PLAN L-3 is already over budget). The key is the TeX itself (display maths prefixed `D:`), rows are insert-only (a stored rendering never changes under a question), readable by every signed-in user, and a CHECK constraint refuses anything that can run or load (scripts, event attributes, `href`, `data:`, `@import`). MathJax is **not** in the app bundle: `scripts/vendor-mathjax.mjs` copies its 2 MB browser build into `apps/mobile/public/vendor` and the importer screen loads it from our own origin, once, the first time it checks a file with maths (no CDN, nothing extra for students to download). A question whose maths won't render is left out of the import. — Claude, prompt 21.
104. **Duplicates: exact match on the normalised stem + its options, then trigram similarity ≥ 0.85.** The key is the stem plus the option texts sorted (shuffled options are the same question; the same stem with different options is not), normalised for case, spacing, punctuation, Urdu harakat and Urdu digits. The server (`import_find_matches`, pg_trgm GIN index on `question_match_text(body)`) only narrows the field to candidates at ≥ 0.5 in the same subject; the final call is made in core, so the app, the tests and the report always agree. An exact match is never imported again; a close one is flagged "nearly the same" and the teacher chooses (left out by default). — Claude, prompt 21.
105. **A bad import is undone by retiring the batch, never by deleting it.** `retire_import_batch(batch, reason)` (reason required, staff or the teacher who imported it) sets its questions and lessons to `retired` and stamps who, when and why on `import_batches`. Nothing is deleted: a paper that already used a question keeps its exact version (rule 3, rule 7). A retired batch takes no further chunks, and its questions drop out of the duplicate search. — Claude, prompt 21.
106. **A second file for the same topic adds to it.** Topics and concepts are matched by title (case, spacing and punctuation ignored) inside the chosen chapter, so re-running a C1 prompt, or importing concept by concept, extends the topic instead of twinning it; a lesson of the same kind that is already there is left out rather than replaced.
